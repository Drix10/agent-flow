## 2. Answers
a. `git reset --hard` logged rule name? YES but indirect: `bulk-git-protected` (G:1388, message G:1369), not a reset-specific name; only fires when manifest.protected_paths is non-empty (G:1367) and ALLOW_PROTECTED unset; with no protected paths it is allowed (hardening.test.js:1296). Reviewer/qa get `read-only-role` instead (G:1725; replay). (replay: implementer and roleless -> bulk-git-protected with protected_paths set.)
b. core.hooksPath its own block? NO. Logged as `no-verify` (G:1122 and G:1684), same name as --no-verify; the audit `reason` text differs ("changing core.hooksPath disables...") but there is no distinct rule string. Reads (`config --get`) are allowed (G:1683, hardening.test.js:518; replay).
c. `source` field (live vs test/probe)? NO. Entry written by appendAudit (state.ts:102-118): `{at, ...entry, prev, hash}` (or `{at, ...entry, unchained:true}` when lock times out, state.ts:113). A guard block entry's own fields: Pi PG:89 = event:"guard_block", role, tool, target, rule, reason; CLI BIN:1306 = event, harness:"claude", role, tool, target, rule, reason. Full line = at, event, [harness], role, tool, target (redacted/240-char command or path, guard.ts:1196-1208), rule, reason, prev, hash. Absent: source, cwd, session id, agent_type/subagent id, manifest hash, override flags in effect, command hash, allow decisions. Tests and probes write the same shape into whatever root they run in; nothing marks them.
d. Override/approval path today: only static env vars set by whoever launches the process: AGENT_FLOW_ALLOW_PROTECTED=1 (PG:33, BIN:1301), AGENT_FLOW_ALLOW_SECRET_READ=1 (PG:34, BIN:1302), AGENT_FLOW_WORKTREE/ROLE (identity, not override). Session-wide, binary, no scope, no expiry, no reason, NOT logged when used (an allowed call is never audited; nothing records that an override was active). They do not lift no-verify/force-push/push-default-branch/ref-rewrite/tamper-proof/secret-read-with-deny... (secret-read is lifted by ALLOW_SECRET_READ; push/no-verify rules take no override argument: decideGit(gc, protectedBranches) G:1120). confirm.ts (extensions/lib/confirm.ts:23-34): requireConfirmation(ctx,title,msg) -> if Pi has UI, ctx.ui.confirm dialog (declined -> throw), returns "ui"; else if AGENT_FLOW_HEADLESS_WRITES=1 returns "headless-env"; else throws. Used ONLY by Pi tools bootstrap_write (bootstrap.ts:139), risk_baseline_update (risk-auditor.ts:57), stale_repair (stale-detector.ts:54), which then log `confirmed_via: ui|headless-env` (bootstrap.ts:146, risk-auditor.ts:59, stale-detector.ts:60). It is a human-in-the-loop gate for agent-flow's own writes, completely unconnected to guard decisions (guard.ts imports nothing from it). It is "half" of an override channel only in the sense that the approval is logged with a via tag; it has no scope (which rule/command/path), no expiry, no approver identity or reason, no signature, no per-call token, and it does not exist on Claude/Gemini/Codex/Cursor/OpenCode paths (those hooks are non-interactive). So: not usable as the channel; at most a pattern to copy (via tag in audit).
e. Push to default branch configurable per repo? NO. Always blocked for every session, role or not (G:17-19 header, G:1184). Default protected set = {main, master} + manifest default_branch (G:1686-1687; same set built G:1939 for MCP). No protect/allow-with-approval/forbid knob; ALLOW_PROTECTED does not apply (decideGit has no access to g). Not configurable in schema. force-push, delete, --all, bare push, HEAD/@/glob refspecs are likewise unconditional.
f. Secret-read decision: path-based, not intent-based. Direct: any non-name-only command whose operands (or `<` input, `--x=path`, `f=@path`, `HEAD:.env`, expanded unquoted glob) resolve to isEnvFile (`.env`, `.env.*`, `.envrc`, `*.env`, not .example/.sample/.template/.dist/.defaults; risk.ts:206-211) or a deny_read match (G:1423-1431, G:1526-1569). First operand of grep/rg/sed/awk is treated as a pattern, not a file, so `grep ".env" src` is allowed (G:1539; hardening.test.js:1447-1452). Recursive: recursiveSearchHit (G:1486-1523) fires for grep/egrep/fgrep with -r/-R/--recursive, and rg/ag/ack, over the operand dirs (default `.`), via firstDeniedUnder (G:1449-1479): walks up to 20,000 entries / 1,500 ms, skips symlinks, .git, node_modules; dotfiles skipped for rg/ag/ack unless --hidden/-u/--no-ignore, but ALWAYS included for grep. It does NOT distinguish direct from incidental: any env file anywhere under the swept tree blocks it. Replay: `grep -rn KEY .` -> secret-read; `grep -r KEY . --exclude=.env` -> still secret-read (--exclude/--include are skipped as value flags, G:1444, never honoured); `grep -rn KEY src` -> allowed; plain `rg KEY` -> allowed (hidden skipped); `rg --hidden` -> blocked; `cat .env.example` -> allowed. Also not consulted: .gitignore, --glob '!.env', -g. Fail-open: if the 20k/1.5 s budget runs out first it returns null (G:1454,1463), so `grep -r x /` on a big tree can pass. Against the 20/25 historical blocks (recursive grep over .env): all would still block today, since the matcher only needs a reachable env file; the only ones that would now pass are those using `rg` without --hidden, or a dir argument that excludes the env's directory. There is no way to express "incidental" (e.g. --exclude honoured, or sweep-with-redaction) and the block reason names the swept dir and the hit file (G:1551), which is the only signal in the audit `reason`.
g. Word-match / substring hazard: YES, in specific places.
   - `core.hooksPath` text scan G:1683: tests the WHOLE raw command (quotes included) for `\bgit\b` and `\bcore\.hookspath\b`. (replay) `git commit -m "doc: explain core.hooksPath risk"` -> no-verify; `echo "core.hooksPath"; git status` -> no-verify. Any slide/PR body/heredoc content in a command that also contains the word git trips it.
   - role-escalation env regex G:1672 (roles only): `\bAGENT_FLOW_[A-Z_]*\s*=` on the whole text incl. quoted data. By reading; not replayed.
   - deny_commands custom patterns G:154 (denycmd.ts) are applied to the whole command text as well as segments, so a user regex like /sudo/ matches inside quoted content; the built-in presets are segment-anchored and safe (denycmd.ts:16-18).
   - `${HOME}` rm regex G:1914 runs on raw text (needs an rm verb before it in the same segment, so low risk).
   - 'sudo': agent-flow has NO sudo rule. The word only appears as a wrapper to peel (G:301, G:733) and in deny presets' PRE (denycmd.ts:13). (replay) `echo "run sudo rm -rf /" > slide.md` and a heredoc slide mentioning sudo -> allowed (null); `sudo rm -rf src` -> blocked as protected-path (because src contains a protected dir), not for sudo.
   - Protected-path text scan (`mentions`, G:453-469, used G:1739/G:1838) only runs when the command is mutating and its writes couldn't be resolved, uses path-boundary regexes (PATH_START/PATH_END G:444-446) and strips data (commit messages, echo/printf, grep patterns, G:474-476, pathWords G:486). Still false-positives on other quoted data: (replay) `gh api -f body="touches src/billing/" ...` and `curl -d "src/billing/x" -o out.txt ...` -> protected-path. echo/redirect-to-file slides are fine.
   - EVIDENCE FROM THIS SESSION (not agent-flow): the separate PreToolUse hook `tracekit/hook.py` blocked two of my Bash calls purely because the command text contained the word sudo (and, in the second, git push -f text): "Blocked by tracekit policy: privilege escalation" / "force push; privilege escalation". Live example of the exact substring hazard the caller is asking about; agent-flow's own matcher does not do that for sudo.
h. Explicit-refspec pushes and `git worktree remove --force`: 
   - HEAD:main -> YES, push-default-branch (G:1179-1184; tests guard.test.js:159, hardening.test.js:154; replay). HEAD:refs/heads/main -> same. `git push origin HEAD` / `@` / `$(...)` dest -> explicit-refspec (G:1182). HEAD:agent/issue-N allowed.
   - `git worktree remove --force` -> NO rule. GIT_MUTATING_SUB lists `worktree remove` (G:220) so reviewer/qa get read-only-role (replay), but implementer/roleless pass (replay: null) unless a protected path is named; `.worktrees/` is not in TAMPER_PROOF (G:91). The CLI twin `agent-flow worktree remove N --force` is blocked for every role except orchestrator via role-tool (G:1005-1012, test hardening.test.js:547); `agent-flow clean` is blocked for any role (G:1010).
i. Escalation telemetry (force-push soon after a push block)? ABSENT. Each block is an independent line (PG:89 / BIN:1306); no correlation id, no per-session counter, no "retry after block" detection. summarizeAudit (audit.ts:87-141) counts blocks by role and by rule only; its "escalations" are state_transition to "Needs Me" (audit.ts:121), unrelated. A pair `push-default-branch` then `force-push` is only recoverable by reading adjacent lines' `at` and `rule` offline. There is also no session/agent id to tie them.

## 3. Where new behaviour plugs in; replay-test cost
- Single pure-ish entry: `decide(g: GuardInput): GuardDecision | null` (G:1877). GuardInput (G:38-58): {role, toolName, input, cwd, root, manifest, worktree?, allowProtected?, allowSecretRead?, walkLimit?, manifestError?}. GuardDecision = {block:true, reason, rule} (G:60-64); block() G:207-209 is the only constructor, so adding a rule = one `return block("name", ...)`.
- Git rules: `decideGit(gc: GitCall, protectedBranches: Set<string>)` (G:1120), called per segment from decideShellCore (G:1688-1692). New git rules (reset --hard unconditional, worktree remove --force, core.hooksPath as its own name) belong here or in decideGitBulk (G:1366). Push policy would need `manifest` threaded in (today only a Set of names arrives).
- Telemetry/override: audit write sites are exactly PG:89/97 and BIN:1306 (two places to add `source`, `harness`, `cwd`, override fields, session id). appendAudit (state.ts:102) spreads `entry`, so extra fields are free; hash chain covers them automatically.
- Override channel would need: decide() input (g.override or approvals list), a reader in PG:33-34 and BIN:1301-1302, and an audit line when used (absent today).
- Replay-test cost: LOW for git/text rules (pure string work on the command; no fs). MEDIUM for secret-read/protected/confinement rules, which hit the fs (landingPath realpath G:1044, expandGlob G:923, firstDeniedUnder G:1449, scripts statSync/readFileSync G:1821-1827, and `git` subprocesses in reviewedScript G:1804-1810), so a fixture needs a real temp repo (cwd matters; `(command, cwd, role, config)` is already the input tuple, but cwd must exist on disk with the files the case expects).
- Existing style: node:test + node:assert/strict, plain JS importing the BUILT .js (`../extensions/lib/guard.js`, so `npm run build` must precede). Typical case: `decide({role, toolName:"Bash", input:{command}, cwd:dir, root:dir, manifest})?.rule ?? null` against `ledgerRepo()` (hardening.test.js:1253-1265, 1272) or `d(role, tool, input, extra)` helper (guard.test.js:20-24). Closest thing to a replay harness already exists: tests/redteam/corpus.json + tests/redteam.test.js: JSON entries {cmd, expect: block|allow|gap, role?}, one shared manifest and one shared scratch dir (redteam.test.js:15-34). Limits: asserts only block/allow/gap (not the rule name), no per-entry cwd, config or worktree. Extending it with `rule`, `cwd`, and per-entry `manifest` would turn the 158-line corpus into the requested (command, cwd, role, config) -> decision fixtures with very little code. AGENTS.md also demands a regression test per guard change plus CHANGELOG.

## 4. Surprising / broken
1. `harness: "claude"` is hard-coded for every CLI-path block (BIN:1306), so Gemini, Cursor, Codex and OpenCode blocks are all logged as claude; Pi blocks have no harness field at all (PG:89). Any per-harness stat from audit.jsonl is wrong today.
2. Overrides are invisible: ALLOW_PROTECTED/ALLOW_SECRET_READ silently return null (G:1367,1527) with no audit line. Allows are never logged either, so there is no denominator for a false-positive rate.
3. CLI-path guard errors (BIN:1317) and "no hook input" (BIN:1274) are not audited; only Pi writes `guard-error`.
4. ALLOW_PROTECTED is much broader than its name: it also disables bulk-git-protected, catastrophic-delete, obfuscated-command, deny-command (G:1579,1914,1918,1921,1367) while push/no-verify rules ignore it.
5. `core.hooksPath` raw-text scan false-positives on prose (G:1683; replay).
6. Recursive-search sweep ignores --exclude/--include/--glob and .gitignore, and fails open on the 20k-entry / 1.5 s budget (G:1454,1463).
7. `git reset --hard` is only caught when protected_paths is non-empty (G:1367); a repo with no manifest gets no protection and no log line; the rule name (bulk-git-protected) does not say reset.
8. `git worktree remove --force` has no rule for implementer/no-role (replay).
9. Pi hook ignores `workdir`/`dir_path` (PG:70 vs BIN:1290), so a shell call that cds via workdir is judged from the wrong cwd on Pi.
10. Rules with no test asserting the name: obfuscated-command, deny-command, symlink-escape, opaque-script, guard-error.
11. guard-wiring only protects the hook files while protected_paths is configured (G:1067): a repo that sets only deny_read or deny_commands can have its hook config edited.
12. scriptDepth is module-level mutable state (G:1752); safe while decide() stays synchronous.
