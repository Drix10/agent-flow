## S1 | CRITICAL | The push ban the plan builds on is bypassable today by quoting; slices 1-2 add exceptions on top of that parser
Plan sections 2/4 treat "push to main always forbidden" as solid and only change delete/policy. `decideGit` parses `stripQuoted(unquoteBareWords(cmd))` (guard.ts:1667, 1688); a quoted word containing any char outside `[\w./@+:,=%^-]` is blanked to `''`, so the refspec vanishes.
REPLAYED, all role-less, all return null (allowed):
- `git push origin 'HEAD~0:main'`, `git push origin "HEAD^{commit}:main"` (push to default branch)
- `git push origin '+HEAD~0:agent/x'`, `git push origin '+refs/heads/*:refs/heads/*'`, `git push origin $'+b:b'` (force / force-all-branches incl. main)
- `git push origin 'refs/heads/*:refs/heads/*'`, `git push origin "b:${BR}"`
Contrast: `git push origin 'b:main'` -> push-default-branch (bare chars get unquoted first).
FIX (add to Slice 1, before the merged-delete item): "decideGit consumes `lexShell`/`effectiveArgv` words (as decideSecretRead already does), not stripQuoted text. Any push refspec word that is dynamic, glob, or contains `~ ^ { } $ * ?` => `explicit-refspec` block. Fixtures: the 6 commands above expect block." Do this first: every later push exception inherits the hole otherwise.

## S2 | CRITICAL | Self-merge scope (open Q2) is far too narrow; push_policy is meaningless while `gh api` is unguarded
Plan lists `gh pr merge`, `gh api .../merge`, MCP `merge_pull_request`. REPLAYED: ALL of these are allowed for every session (role-less and implementer):
`gh pr merge N --admin`/`--auto`; `gh api repos/o/r/contents/f -X PUT -f branch=main ...` (commit straight to main); `gh api repos/o/r/git/refs/heads/main -X PATCH -F force=true` (force-move main); `gh api -X DELETE repos/o/r/git/refs/heads/main`; `gh api -X DELETE repos/o/r/branches/main/protection`; `gh api repos/o/r/rulesets/1 -X DELETE`; `gh repo edit --default-branch b`; `gh release create v1 --target main`; `gh workflow run deploy.yml`; `gh api graphql -f query='mutation{mergePullRequest|enablePullRequestAutoMerge...}'`; `curl -X PUT https://api.github.com/.../pulls/5/merge`; `gh pr edit 5 --base main`. Also `gh api -X DELETE .../git/refs/heads/b` deletes any remote branch, so the false-block "fix" for merged-branch delete is a pure UX change: the real delete path was never closed.
Also not covered: MCP names beyond 3 hardcoded (guard.ts:1936: `create_branch`, `update_pull_request_branch`, gitlab `merge_merge_request`, any `*_commit` tool); labels that trigger auto-merge workflows; role-less `merge_pull_request` (guard.ts:1945 only gates `role && role!==orchestrator`).
FIX: new Slice 2 rule `remote-write` (all sessions, honouring push_policy): block `gh pr merge`, `gh repo edit|delete|sync`, `gh release create|delete|edit`, `gh workflow run`, `gh secret|variable set`, and `gh api`/`curl`/`wget`/`http` to a forge host with any non-GET method or `-f/-F/--input`, EXCEPT an allow-list (create PR `POST .../pulls`, issue/PR comments, labels other than automerge). Allow-list, not block-list; dynamic URL/method => block. GraphQL: block mutation names `mergePullRequest|enablePullRequestAutoMerge|createCommitOnBranch|updateRef|createRef|deleteRef|updateRepository|updateBranchProtectionRule`. Add: "client-side guard cannot stop a token with admin rights; document that server-side branch protection/rulesets are the real boundary" to docs. Answer open Q2 = yes, and the doc-only fallback ("ban only guarantees a PR was used") is false while `contents PUT branch=main` is open.

## S3 | CRITICAL | Manifest trust: corrupting CONTEXT_MANIFEST.json drops every floor; new keys would be agent-editable
REPLAYED (r2.mjs, repo with committed manifest deny_read=["secrets/**"], deny_commands preset database):
- baseline: `cat secrets/db.txt` -> secret-read; `psql -c "DROP TABLE users"` -> deny-command.
- role-less `Write` of `{` to CONTEXT_MANIFEST.json -> ALLOWED (governance is implementer-only). After that, `loadManifestForGuard` returns manifest=null+error (manifest.ts:332-334, `r.error !== not_found` branch skips the committed floor), and the same two commands -> ALLOW. Only file writes are refused (`manifest-unreadable`), and rewriting the manifest is explicitly exempt (guard.ts:1891).
- With a valid edit: guard reads `default_branch` from the DISK copy (replayed: disk `agent/x` was loaded). protected_paths/deny_read/deny_commands have an additive floor; nothing else does (FLOORED_KEYS applies only to `trustedManifest`, not to the guard).
Impact on plan: `push_policy` and any "default branch" used for the merged-branch probe are agent-settable by a role-less session in one Write call (role-less includes the 01a1ba9a session type).
FIX: (a) "On manifest parse error, the guard uses the HEAD/default-branch committed manifest as the manifest, with `manifestError` still set"; (b) "`push_policy` effective value = strictest of disk, HEAD, default-branch copy (forbid > approve > allow); a relaxation is honoured only from the default-branch copy"; (c) "`default_branch` for push rules/probe comes from `git ls-remote --symref`/the default-branch copy, never from the disk manifest (disk may only ADD protected names)". Tests: corrupt-manifest fixture expecting secret-read/deny-command still block.

## S4 | HIGH | Merged-branch delete (Slice 1): concrete bypasses, and "fail closed" does not hold as structured
CODE: `decideGit(gc, protectedBranches)` is pure and gets no cwd/-C/remote/manifest (guard.ts:1120, called per segment at 1688 with no cwd tracking); `segments()` ignores `cd`. Any probe must be threaded in and run where the push runs.
REAL-GIT experiments (temp bare remote):
1. Alias refs: `git push origin :heads/main` really deletes remote `main` (verified: `[deleted] main`). `heads/main` is not stripped by the `refs/heads/` regex (guard.ts:1179), so it is not in protectedBranches; today only the delete rule stops it (REPLAYED: force-push). `git rev-parse heads/main` resolves, so `merge-base --is-ancestor heads/main origin/main` says "merged" -> the new exception ALLOWS it. Also `:Main` on case-insensitive remotes, `--delete heads/main`, `--delete refs/heads/main`.
2. "Merged" is true for identical tips: a `release/v1`, `production`, `staging` or `develop` branch at main's commit is fully merged (verified yes). Deleting it is allowed by the plan text.
3. Local-vs-remote spoof: `git branch -f agent/x main` (allowed role-less, REPLAYED: `git branch -f main b` and `git symbolic-ref` allowed) makes local `agent/x` look merged while remote `agent/x` is unmerged (verified). Probe on local refs destroys remote work. Likewise `git branch -f main <b-tip>` or `git symbolic-ref refs/remotes/origin/HEAD ...` changes what "default" means; `defaultBranch()` (git.ts:46-58) falls back to local main/master/trunk/develop and finally the CURRENT branch (`b` is merged into itself).
4. Stale `origin/<b>`: someone pushes to the remote branch after the last fetch; local `origin/b` still looks merged (verified). Delete destroys their commits.
5. Wrong repo/remote: `cd ../other && git push origin :b`, `git -C ../other push ...`, `git push https://x/y.git :b`, `--repo=`: probe must use the push's directory and resolved remote URL; the guard does not track `cd` for git segments.
6. Multiple refspecs / flags: allow must apply per refspec and ONLY when delete is the sole trigger. `forced` is one OR-chain (guard.ts:1156-1163); `--delete --force`, `--delete --mirror`, `--delete b --prune`, `-fd`, `:b :main`, `--delete b main` must stay blocked (all currently block; REPLAYED).
7. Fail-closed trap A: `rev-list origin/main..b --count` or `git branch --no-merged` returning empty stdout on error reads as "0 unmerged" = merged. Use only exit-status of `merge-base --is-ancestor` with status===0 and nothing else.
8. Fail-closed trap B: an exception from the probe falls into guard-error handling: CLI `cmdGuard` returns exit 0 (ALLOW) when no role and no manifest (bin/agent-flow.js:1265-1268 `fail()`), Pi returns undefined (extensions/guard.ts:92). So an unconfigured session fails OPEN on a probe exception.
FIX (replace the bullet): preferred = move merged-delete to Slice 2 and ship only the reroute text in Slice 1 ("`gh pr merge --delete-branch` or enable repo auto-delete of head branches"). If kept: "Allowed only when ALL hold: single refspec `:<name>` or `--delete <name>`; `<name>` matches `^agent/` (or manifest `branch_prefix`) and is not default/protected/release*/prod*/staging/develop/trunk; remote is a configured remote name (not URL, no --repo) and cwd resolved by the cwd-tracking lexer; remote sha from `git ls-remote <remote> refs/heads/<name> refs/heads/<default>` (default from `ls-remote --symref`), commits present locally, `merge-base --is-ancestor` status===0, tip(<name>) != tip(default); wrapper catches every exception and returns the existing block. Fixtures for items 1-8 above."

## S6 | HIGH | Secret-read: the two planned changes miss the live leaks; "honour exclusions" is the wrong tool
REPLAYED allowed (role-less; `.env` at root, `pkg/.env.local` nested):
- Dynamic dir operand is skipped (`if (w.dynamic) continue`, guard.ts:1516): `grep -r KEY $PWD`, `$(pwd)`, `"$(git rev-parse --show-toplevel)"`, `rg --hidden KEY "$PWD"`.
- Glob operand never expanded for sweeps: `grep -rn KEY *`, `./*`, `pkg/*` (grep -r descends into hidden files of every dir).
- rg whitelist globs: `rg KEY -g '.env*'`, `-g '*.env'` allowed; real rg treats `-g` as override that includes hidden files (rg not installed here, from rg docs; unverified live). `-g '.env'` blocked only by accident.
- `git grep --no-index KEY` allowed and, verified on real git, prints `.env:SECRET=1` for a gitignored .env. `find . -name '.env*' -exec cat {} \;`, `... | xargs cat`, `cat $(find ...)` allowed.
- Budget fail-open: `grep -r KEY /` allowed (walk exhausts 20k, returns null, guard.ts:1454/1463) as the plan says. But "fail closed" on exhaustion blocks `rg KEY` (counts hidden entries even though skipped, line 1463 precedes the hidden skip) and `grep -r x .` in any repo with >20k non-node_modules entries (dist/build/target/vendor) and flakily on cold Windows disks (1.5 s wall clock): same command blocks or passes depending on disk cache. Not verified at scale.
- Exclusion spoofing if honoured: grep `--exclude` is basename-glob with last-match-wins vs `--include`; `--exclude=.env` does not exclude `.env.local`; `--exclude-from=<agent-written file>` unevaluable; rg `-g` has gitignore semantics (anchoring, `**`, order, `!`), `--no-ignore`, `-uu`, `RIPGREP_CONFIG_PATH` env/rc files, `--ignore-file`. BSD vs GNU grep differ. A re-implemented matcher WILL diverge.
FIX (replace both bullets): (1) Do NOT honour excludes. Block message reroutes to forms that already pass and cannot read env files: `git grep -n PAT` (tracked only), `rg PAT <dir>` w/o hidden flags, or `grep -rn PAT src/`. Fixture: those allowed, `--exclude` forms still block. (2) Fail-closed only when the tree is a git repo AND enumeration is cheap: enumerate candidates with `git ls-files -z --cached --others --ignored --exclude-standard` filtered by isEnvFile/deny_read (C speed, deterministic), fall back to the walk; on walk exhaustion outside a repo, block only if hiddenToo. (3) Dynamic/glob operand on a recursive search => treat as `.`; `--no-index`/`--untracked` on git grep => walk; `find ... -exec|xargs` with a reader verb => block when any `-name` pattern matches env names or tree contains env files. (4) Add a perf fixture (30k files) to the test plan; do not ship fail-closed without it.

## S7 | HIGH | Positional `git config core.hooksPath` read: a naive parse widens existing holes; swapping raw-text for argv removes the only net that catches them
REPLAYED existing holes (role-less): `git config --show-scope core.hooksPath /dev/null` ALLOWED and is a real write (verified: rc=0, value set; git rejects `--show-origin` but not `--show-scope`) because `--show-\S+` is treated as a read marker (guard.ts:1121, 1683). `git config core.hooks''Path /x`, `K=core.hooks; git config ${K}Path /x`, `git config core.hooks$(echo Path) /x` ALLOWED. `GIT_CONFIG_GLOBAL=/tmp/evil git commit`, `GIT_CONFIG_SYSTEM=...`, `git -c include.path=/tmp/evil commit`, `git config alias.ci 'commit --no-verify'` then `git ci`, `git config -e` (with GIT_EDITOR), and `echo '[core]\nhooksPath=/x' >> .git/config` / `sed -i ... .git/config` ALL ALLOWED for role-less (tamper-proof only covers .git/hooks and destructive .git ops). The raw-text scan (guard.ts:1683) currently catches the quoted/escaped variants; dropping it is a regression unless replaced.
How to tell read from write reliably (git's own rule): after removing global flags, if any action flag is present (`--get* --get-regexp --list -l --get-color* --get-urlmatch`) it is a read; if any of `--add --unset* --replace-all --rename-section --remove-section -e --edit --set-*` it is a write; with NO action flag, exactly ONE non-option positional (after dropping option values of `-f --file --blob --default --type --comment`) is a read, 2+ is a write. `--show-origin/--show-scope/--name-only/--null/-z/--global/--local/--system/--worktree` are neutral modifiers, never read markers.
FIX: Slice 1 text: "hooks-path rule on lexShell argv: dynamic word anywhere in `git config|-c|--config-env` => block; positional-read per the rule above; keep the raw-text scan as a fail-closed fallback only when argv parse yields a dynamic word, and restrict it to the git segment (not `commit -m`/`echo` data) so the prose false positive goes away. Also block: `-c`/`--config-env` for `core.hooksPath|include.path|alias.*|core.fsmonitor|core.sshCommand`, env `GIT_CONFIG_{COUNT,KEY_*,GLOBAL,SYSTEM,PARAMETERS}`, `git config alias.*` containing `--no-verify`/`!`, writes to `.git/config|.git/info|.git/hooks` for all sessions." Fixtures: every command above.
